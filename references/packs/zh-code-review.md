# Scene pack — 程式碼審查意見（ZH）

適用：PR 留言、issue 回覆、review comment、討論串回應。中文為主、術語夾英文的工程對話。

信心標記：〔繼承〕= 沿用母技能已驗證的規則；〔推論〕= 跨語言合理延伸，中文側沒有量測基線；〔臆測〕= 憑寫作經驗判斷，讀者可以推翻。本檔案沒有任何中文語料的統計數字，因為不存在。

---

## 1 骨架〔繼承〕

1. **先給判斷。** 第一句就是結論：blocking、nit、問題、或「不做」。理由放後面，需要多少寫多少。
2. **指到證據。** `UserService.java:142`、commit SHA、原封不動貼的錯誤訊息、文件連結。談程式碼的主張要指得到那行程式碼。
3. **不確定就問，不要斷言。** 「這裡吞掉 exception 是刻意的嗎？」勝過三段假設性推論。
4. **blocking 與 nit 明確分開**，用這個 repo 既有的分法。
5. **不要複述提交者的問題**。討論串裡已經有了。
6. **不要開場讚美、不要罐頭同理、不要結尾祝福。**
7. **長度與風險成比例，而且不要每則留言長得一模一樣。** 有些留言就是三個字，有些是一整段。

## 2 中文過度體貼〔推論〕

這是中文 review 最主要的失效模式，也是本 pack 存在的理由。中文的禮貌層比英文厚，AI 會把它疊到「提交者讀不出這是擋下」的程度。**blocking 讀起來就要像 blocking。**

| 徵候 | 訊號（可搜） | 預設動作 | 保留條件 |
|---|---|---|---|
| 稀釋 blocking | 「或許可以考慮一下」「要不要看看」「不知道這樣會不會比較好」「這邊可能可以」 | 換成直述句加嚴重度標籤：「blocking — 這行會 NPE。」 | 這些句式在 nit 或真的只是偏好時完全正常，保留 |
| 讚美開場 | 「整體寫得很好」「這個 PR 很棒」「感謝你細心的回報」「辛苦了」 | 刪，第一句直接給判斷 | 真的值得謝：第一次貢獻、對方花了力氣做重現、對方回報了你沒發現的問題。謝一句，不寫成公式 |
| 讚美三明治 | 好話 → 問題 → 好話 | 拆掉，只留中間那層 | 無 |
| 自我懷疑尾巴 | 「僅供參考」「以上純屬個人意見」「不知道我理解得對不對」「小小建議」 | 刪。真的不確定就寫成問句（見骨架 3），不要寫成免責聲明 | 無。免責聲明和提問是兩件事：提問要求回答，免責聲明是把責任丟回去 |
| 波浪號與 emoji 軟化 | 「改一下～」「這樣可以嗎😅」 | blocking 一律拿掉 | nit 可留，前提是這個 repo 既有的 review 語域本來就這樣。先讀幾則既有留言再決定〔繼承〕 |
| 罐頭同理 | 「我完全理解你的困擾」「這確實會讓人很挫折」「辛苦你了」 | 換成你真正需要的那個重現資訊 | 無 |
| 結尾祝福 | 「希望這對你有幫助！」「有任何問題歡迎隨時提出～」「再麻煩你了，謝謝！」 | 停在內容 | 單獨一句「麻煩了」在臺灣工程語域是自然的，不算樣板；但不要和其他三種客套疊在一起 |
| 複述對方 | 「如果我理解正確的話，你的意思是…」 | 刪 | 對方寫得真的有歧義時保留，且要寫成二選一：「你是指 A 還是 B？」 |
| 請求句式包裝擋下 | 「請問可以幫忙改一下嗎」 | blocking 用直述或祈使：「這裡要改成 X。」 | 對外部貢獻者可以多一句指路（文件連結、慣例說明），但不得改變嚴重度標籤 |
| 對人不對事 | 「你的函式」「你這樣寫」 | 改成「這個函式」「這行」 | 討論串裡明確要區分兩個人的實作時 |
| 每則留言同一個結構 | 十則留言都是「讚美＋問題＋建議」 | 打散。有些留言只寫「nit: 拼字」 | 無〔繼承〕 |
| 承諾代替動作 | 「我之後會看一下」而修法就在手邊 | 直接做，然後貼 commit | 真的排不進這輪時，寫成 issue 編號，不要寫成口頭承諾〔繼承〕 |

### 改寫示例

- ✗「辛苦了！整體看下來寫得很好 👍 這邊或許可以考慮一下要不要處理一下 null 的情況？當然也可能是我想太多，僅供參考～」
- ✓「blocking — `UserService.java:142`：使用者沒設過大頭貼時 `profile` 是 null，這行會 NPE。加 null 檢查，或改回傳 `Optional`。」

- ✗「這裡我覺得可能會有一點點效能上的疑慮，不過應該還好，你參考看看就好。」
- ✓「這個迴圈裡每圈都打一次 DB（`sync.go:88`）。一百筆就是一百次查詢，改成一次 `IN` 查詢。blocking。」

- ✗「這個 PR 很棒！只是我想確認一下，這裡的例外處理是不是有什麼特別的考量呢？如果沒有的話或許可以再看看？」
- ✓「`sync.go:88` 這裡吞掉 exception 是刻意的嗎？如果是，加一行註解說原因；如果不是，這是 blocking。」

- ✗「這個功能我們暫時可能還沒辦法支援，可能要再評估看看，還請見諒。」
- ✓「不做。#388 討論過，決議是保留舊行為到 v3。」

## 3 嚴重度標籤與句型〔推論〕

臺灣工程圈直接用英文標籤，這是既定語域，硬翻成「阻擋性問題」反而更難讀。標籤放**句首**，不要藏在段落中間。

| 標籤 | 意思 | 句型 |
|---|---|---|
| `blocking:` | 不改不能 merge | 「blocking — `檔案:行`：會發生 X，因為 Y。改成 Z。」 |
| `nit:` | 改不改都行，不擋 | 「nit: `getUsreById` 拼錯。」一行就好，不要解釋。 |
| `question:` 或直接問 | 你不確定，需要對方回答 | 「這裡是刻意的嗎？如果 `id` 是空字串會走到哪？」 |
| `suggestion:` | 有更好的寫法，但不擋 | 「suggestion: 這段可以用 `strings.Cut` 少一次配置。不擋。」 |
| `LGTM` | 沒有 blocking，可以 merge | 只有在真的沒有 blocking 時才寫。有 blocking 還寫 LGTM 是最嚴重的失效 |

其他保留英文的詞：edge case、refactor、race condition、breaking change、rollback、revert、deprecate、fallback、trade-off、TODO、flaky。

不確定的標準寫法〔繼承〕：「不太確定 —— 這在 2.4 上重現得了嗎？我這邊測不出來。」比三段對沖有用。

## 4 支語陷阱〔推論〕

review 留言是口語體，支語滲透最快。

| 支語 | 臺灣用法 | 備註 |
|---|---|---|
| 對齊（指取得共識） | 同步、確認一下 | 「這個我們對齊一下」→「這個我們先同步一下」。指排版或記憶體 alignment 時保留 |
| 落地 | 實作、上線 | |
| 顆粒度 | 細緻程度、粒度 | 「鎖的顆粒度」→「鎖的粒度」或「鎖切得多細」 |
| 復用 | 重複使用、再利用 | |
| 健壯 | 穩健 | |
| 冗餘（贅義） | 多餘、重複 | **redundancy 意義下的「冗餘」是臺灣正確用語**（冗餘備援、冗餘電源、RAID 的冗餘）。判準：指刻意保留的備份→保留；指不必要的重複→改「多餘」 |
| 調用 | 呼叫 | 「這裡調用了兩次」→「這裡呼叫了兩次」 |
| 報錯 | 錯誤訊息、出錯、拋例外 | **口語 review 留言可接受**（「它報錯了」是臺灣工程師實際會說的話）。但寫進 PR 描述、commit message、對外文件時改掉 |
| 兜底 | 保底、後備、fallback | |
| 埋點 | 事件追蹤、打點 | |
| 提測、聯調 | 送測、整合測試 | |
| 打日誌 | 寫 log、記 log | |
| 質量 | 品質 | |
| 內存／緩存／隊列 | 記憶體／快取／佇列 | |
| 用戶／默認／項目／優化／信息 | 使用者／預設／專案／最佳化／資訊 | Layer 1 已擋，此處僅提醒 review 口語同樣適用 |

## 5 與 scope 的互動

- 刪客套（讚美開場、免責尾巴、祝福句）多半是**整句刪**。bounded scope 下進待確認清單；in-place scope 下只標記。
- 但**把 blocking 從軟化句式改回直述，屬於句內改寫**，任何 scope 都可以做，因為那不是刪除，是把嚴重度訊號改對。這是本 pack 唯一一條在 in-place scope 下仍可主動改寫的規則〔臆測〕。
- 不得代替審查者更動嚴重度判斷：軟化的句子改回直述時，維持原本被稀釋的那個嚴重度，不要順手升級成 blocking。若原文含糊到判斷不出嚴重度，標記給使用者決定，不要猜。

## 6 重讀檢查

1. 第一句是不是判斷？（不是的話，前面那句刪掉。）
2. 每一則 blocking，提交者能不能在三秒內看出這是 blocking？
3. 每一個關於程式碼的主張，有沒有 `檔案:行`？
4. 有沒有一則留言只有一句話？（十則都是三段式就是機器寫的。）
5. 搜尋是否為零命中：「或許可以考慮」「僅供參考」「小小建議」「希望這對你有幫助」「整體來說寫得很好」「我完全理解」。
6. 有寫 LGTM 的話，串裡是不是真的沒有 blocking？
7. 支語表左欄零命中（「冗餘」「報錯」需人工判斷語境）。
