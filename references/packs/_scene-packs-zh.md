# Scene Packs / 可直接發場景包

> 本檔案是解釋、示例與操作細則；行為合同的單源是 `SKILL.md`，兩處表述不一致時以 `SKILL.md` 為準。

Scene Packs 是面向可發布文字的子場景策略。它不替代 [場景禁改表](../scene-guardrails.md)、[Protected Spans](../protected-spans.md) 或 `Tier` 判斷；只要文字本身像 README、release note、forum post、issue reply、API reference 或 FAQ，就進一步判斷「這段應該像哪一種發布文字」。

使用順序：

1. 先判大場景：`chat / status / docs / public-writing`
2. 先劃 protected spans：版本號、路徑、連結、命令、引用、編號、責任歸屬都不能漂
3. 再看是否命中本檔案的 scene pack
4. 最後按 scene pack 的發布目的收束語氣；如果它同時像 `docs / status`，取更保守的保真邊界

預設不要因為 scene pack 新增全域性詞條。只有新樣本已經超出現有問題族，且會改變誤殺邊界時，才考慮補 `phrases` 或 `structures`。

## `README`

預設目標：

- 第一屏能讓讀者快速知道：這是什麼、給誰用、解決什麼問題。
- 語氣可以有個性，但不能只剩願景、價值和姿態。

必須保留：

- 專案名、目標使用者、核心能力、支援平台
- 命令、安裝方式、檔案路徑、連結
- 已有 benchmark 數量、版本號和能力邊界

**「保留路徑」不等於「保留錯的路徑」** `[inference]`：README 是最容易累積作者自己絕對路徑的地方 —— `D:\我的專案\tool\` 這種寫法看起來很具體，所以會通過審查，但對每一個不是作者的讀者都跑不動。逐條套 [professional-pass](../professional-pass.md) 的 check 11：這個位置是平台定的（安裝根目錄、`C:\ProgramData\…`）還是作者定的（他的 clone 位置）？前者留，後者改成 repo 相對路徑或 `<repo>` 這類佔位符，並在該節說明命令從哪裡執行。

同一份 README 裡 Quick start 用相對路徑、檔案表用絕對路徑，是這個病灶的典型形態 —— 通常代表其中一份是後來補的，另一份沒跟著更新。

優先刪除：

- `AI 全面重塑開發正規化`
- `面向未來`
- `深度賦能`
- `內容生產鏈路`
- `價值閉環`
- 沒有具體能力或證據支撐的 `真正能 / 做快做穩 / 更像人寫的` 等自我宣傳結果句
- 只說「先進 / 智慧 / 全方位」但不說具體做什麼的句子

預設力度：

- `standard`
- 如果 intro 只剩口號，可以升到 `aggressive`，但不能編造專案能力

誤殺邊界：

- README intro 允許一句有辨識度的定位句
- `CLI / API / benchmark / Codex / ChatGPT` 等專案術語應保留
- 不要把 README 改成社交媒體短帖

Before:

> 在 AI 全面重塑開發正規化的今天，我們打造了一款真正面向未來的中文表達最佳化工具，深度賦能開發者的內容生產鏈路。

After:

> `說人話` 是一個中文優先的 rewrite skill，用來把 AI 寫出來的套話、表演感和工程師腔改回自然表達。適合 README、release note、issue 回覆和日常協作文字。

## `release-note`

預設目標：

- 讓讀者快速知道這一版改了什麼、怎麼驗證、有沒有破壞性變化。
- 優先列表化，少寫發布宣言。

必須保留：

- 版本號、日期、檔名、配置項、issue / PR 編號
- 變更類型：新增、修復、調整、測試
- 已知限制和遷移提示

優先刪除：

- `Release Highlights` 後面只寫空泛升級
- `系統性升級`
- `全新躍遷`
- `感謝所有使用者持續支援`
- `共同見證`
- 沒有來源的效能、效率、使用者反饋資料

預設力度：

- `standard`
- 如果缺少具體 changelog，不要編造；改成提示「這裡需要補具體變更」

誤殺邊界：

- release note 可以正式、簡潔、列表化
- 不要為了「像人」把 changelog 列表改成故事
- 不要刪版本號、檔案路徑、case 數量和 PR / issue 編號

Before:

> 本次版本是一次面向真實場景的系統性升級，感謝所有使用者的持續支援，讓我們共同見證中文 AI 寫作體驗的全新躍遷。

## `forum-post`

預設目標：

- 像維護者在社群裡講真實觀察：做了什麼、發現什麼、哪裡還不穩、想要什麼反饋。
- 允許口語，但要有具體經歷支撐。

必須保留：

- 時間、動作、具體檔案、樣本數量、觀察到的問題
- 原作者真實態度和社群語氣
- 連結、命令、版本號和被討論詞

優先刪除：

- 公司公告腔
- `系統性重塑`
- `使用者痛點`
- `多元場景`
- `方法論閉環`
- `穩穩接住核心訴求`

預設力度：

- `standard`
- 如果帖子本來有具體經歷，只清理姿態層，不要改成正式公告

誤殺邊界：

- 具體經歷後的口語詞可以保留
- 社群帖允許「踩坑 / 折騰 / 還差一點」這類真實語氣
- 不要把個人檢討改成 README 或 release note

Before:

> 折騰這個工具一個月後，我深刻意識到，中文 AI 寫作治理不是一次簡單的詞表擴張，而是一場圍繞真實表達場景的系統性重塑。

After:

> 做這個工具一個月後，我發現光刪詞表不夠。README、release note、issue 回覆和論壇帖看起來都是「公開文字」，但改法其實不一樣。

## `issue-reply`

預設目標：

- 先回答問題是否成立，再給復現狀態、判斷和下一步。
- 不做客服式安撫，不替維護者承諾未排期能力。

必須保留：

- bad case 原句、場景標籤、復現結果
- issue / PR 編號、檔案路徑、規則名、benchmark 編號
- 「已確認 / 未復現 / 需要更多樣本 / 會補測試」的狀態

優先刪除：

- `感謝寶貴反饋`
- `你問到了核心`
- `我們已經充分接住這個場景`
- `持續最佳化相關能力`
- `如果你願意我可以繼續幫你`

預設力度：

- `minimal` 或 `standard`
- 有具體技術資訊時保守處理；沒有具體下一步時，不要編造排期

誤殺邊界：

- issue 回覆可以短、硬、直接
- `bad case / docs / SNF / benchmark / repro` 是維護語境裡的正常術語
- 不要把明確的維護回覆改成社交式寒暄

Before:

> 感謝你非常寶貴的反饋！你這個問題問到了專案體驗的核心。我們已經充分接住了這個場景，也會在後續版本中持續最佳化相關能力。

After:

> 收到，這個 case 我能復現。它屬於 `docs` 場景裡的誤殺，下一版先補一條 SNF；如果現有規則已經能放行，就只加迴歸用例。

## `commit-message`

涵蓋 commit 訊息與 PR 內文。

預設目標：

- 第一行說清楚**改了什麼**，不是改了哪些檔案。
- 內文寫**為什麼要改、為什麼是這個做法**，不是把 diff 用散文重講一遍。

必須保留：

- 檔案路徑、函式名、issue／PR 編號、版本號、錯誤訊息原文
- 破壞性變更與遷移步驟
- 實際的行為差異

### 署名（硬性規則）

- `Co-Authored-By:` **只列真人** —— git 設定裡的作者、GitHub 登入者，或使用者在該次對話中實際指名的協作者。
- **不要自己加 AI 工具的 `Co-Authored-By:` trailer。** 沒有第二個可署名的人，就整行不寫。
- PR 內文結尾**不掛生成工具的註腳**（`🤖 Generated with …` 這類）。
- 使用者明確要求掛某個 trailer 時照做。本節管的是**預設不要自己加**。

這條**不是風格偏好，是保真問題** `[inference]`：commit 歷史與 PR 是歸屬紀錄，工具署名會讓 `git blame`、貢獻統計和 review 責任失真 —— 它把一個沒有做出判斷、也不承擔後果的對象寫進責任鏈。因此它比照第 1 層處理：**不佔 calibration 預算，不因 edit scope 豁免**，`in-place` 底下照樣拿掉。

優先刪除：

- `本次提交旨在……`、`為了提升程式碼品質` 這類把 diff 重講一遍的開場
- `優化了相關邏輯`、`完善了部分功能` 這種沒有具體物件的說法
- 生成工具的註腳與 AI co-author trailer
- 結尾的 `歡迎 review`、`有問題請隨時提出`

預設力度：

- `minimal`
- commit 訊息本來就短。這裡的病灶多半是「說了等於沒說」，不是「話太多」

誤殺邊界：

- 一行的 commit 訊息完全正常，不要為了「更完整」硬加內文
- `fix` / `chore` / `refactor` 這類 conventional commits 前綴是慣例，不是模板感
- revert、merge、release 的自動產生訊息照原樣，不要改寫
- 引用的錯誤訊息、堆疊、指令照原樣

> 本次提交旨在對專案的路徑處理邏輯進行優化，提升了程式碼的健壯性與可維護性。

## `api-reference`

預設目標：

- 讓讀者快速確認介面用途、呼叫條件、請求約束、響應語義、錯誤含義和恢復動作。
- 保持可掃描結構；參數列、欄位列表和程式碼示例不改成敘事段落。

必須保留：

- HTTP method、路徑、介面名、鑑權方式
- 欄位名、型別、格式、required / optional、預設值、範圍、單位、依賴關係和列舉
- 狀態碼、錯誤碼、程式碼、JSON、命令、連結、版本、速率限制和已給出的恢復步驟

優先刪除：

- 介面說明前的價值拔高、宣傳口號和元評論
- 重複解釋 endpoint 或引數名的空話
- 沒有來源的行業判斷、效能保證和可用性承諾
- 把明確動作藏進 `能力建設 / 機制實現 / 體驗升級` 的名詞化外殼

預設力度：

- `minimal`
- 只改說明文字；表格、列表、程式碼塊、JSON 和識別符號不動

誤殺邊界：

- 原文沒有的預設值、條件、錯誤原因、恢復時間、相容範圍一律不補；缺失就按 `audit-only` 標待確認
- 狀態碼按當前介面裡的真實語義理解，不機械套固定文案
- 系統主語和真實被動語態可以保留；不要為了主動、口語而改變責任主體
- 不為避免重複而給同一欄位換同義叫法，不把 optional 改成 required，不換算數字或單位

## `faq`

預設目標：

- 問題範圍準確；答案先給結論、判斷或動作，再給必要條件、步驟、限制和下一步。
- 標題保留使用者會實際檢索的問法，不改成宣傳標題或抽象分類。

必須保留：

- 問題裡的物件、版本、條件、否定和例外
- 答案裡的期限、費用、支援承諾、責任主體、命令、連結、路徑和編號
- 排障步驟的順序與分支

優先刪除：

- 重複一遍問題才開始回答
- 假共情、客服寒暄和銷售式安撫
- `大家都知道 / 通常都可以 / 一定沒問題` 這類無源保證
- 與答案無關的價值總結

預設力度：

- `minimal`
- 已經短、硬、可執行的答案整體放行

誤殺邊界：

- 不把採訪、討論引用或所有帶問號的段落都識別成 FAQ
- 不把 `可能` 改成 `會`，不把 `部分使用者` 改成 `所有使用者`，不擴大支援承諾
- 不軟化 `不支援 / 必須 / 不會` 等真實限制，也不改期限、政策和操作路徑
- 缺條件或來源時標出缺口，不自造 SLA、恢復時間、預設路徑或客服電話
