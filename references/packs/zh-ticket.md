# 場景包 — 工單、需求單、bug 回報

適用：issue、工單、任務單、需求單、你自己開的 bug 回報。（回覆別人的 issue 屬於另一個包。）

信心標示：〔骨幹〕＝繼承自 sepia 英文場景規則，其原始依據為英文語料（grounded）。〔中文推論〕＝把該規則延伸到中文寫作的判斷，無中文語料量測（inference）。

---

## 一、結構骨幹（〔骨幹〕，不因語言改變）

1. **標題寫結果，不寫活動。** 「重新部署後 retry 佇列的 job 會消失」，不是「調查佇列問題」。
2. **驗收條件必須可測**：寫出要跑的指令，與代表「做完了」的輸出。不可測就不算條件。
3. **範圍明確畫到檔案／函式**：哪些在範圍內、哪些明確不在。
4. **bug 單要有完整重現路徑**：版本、指令、輸入、預期與實際（貼真實輸出）、發生頻率。重現不出來就寫你試過什麼。
5. **連結，不要複述**：前一張單、設計文件、告警連結——單一事實來源。
6. **描述從標題結束的地方開始**，不是把標題再寫成句子。
7. **優先級與估時直接寫，不附理由段落。**
8. **空白是合法值**，「N/A」勝過一整段沒有內容的文字。
9. **顯而易見的步驟不寫**（「1. 打開專案 2. 找到該檔案」），只寫不顯而易見的那幾步與確切指令。
10. 判準：接手的人不必再來問問題就能開始，而且知道什麼時候算做完。

## 二、主語問題：工單與事故報告的處理方式不同（〔中文推論〕）

工單正文用**祈使句、不帶主語**是正確的中文，也是正確的工單寫法——因為責任主體已經詞彙化在 assignee 欄位裡了。不要為了「補主體」而在每句話前面加「開發者應該」。

但下列三種句子仍然必須指名，理由與事故文件相同：句子承載了責任或授權。

- **引用他人結論**：✗「已與 PM 同步，可以先跳過驗證。」→ ✓「PM 陳雅琪 08-27 決定這一版先跳過 email 驗證，見 PROD-812。」
- **交付依賴**：✗「等相關團隊提供 API 後即可開始。」→ ✓「等 payments 團隊交付 `POST /v2/refund`（窗口：張立群，預計 09-05）。」
- **例外授權**：✗「經確認可以直接改正式環境設定。」→ ✓「SRE on-call 王思婷同意這次直接改 prod 設定，事後補 PR。」

同樣的反向規則：來源沒有指名的人，不要編。寫 `（待確認）` 並在單子裡指出誰去問。

## 四、中文特有的 AI 痕跡（〔中文推論〕）

| 痕跡 | 修法 |
|---|---|
| 客套開場：「您好，煩請協助處理以下問題，感謝！」 | 刪掉。單子第一行就是問題本身 |
| 標題寫成活動或願望：「最佳化登入流程」「提升系統穩定性」 | 換成結果句：「Safari 17 在登入頁按 Enter 不會送出表單」 |
| 描述複述標題：「如題，登入頁按 Enter 沒有反應，需要處理。」 | 描述從標題結束的地方開始：版本、重現條件、實際輸出 |
| 輕動詞贅語：「進行修改」「做出優化」「予以處理」「實施驗證」 | 「改」「調整」「處理」「驗證」 |
| 模糊時間：「盡快」「近期」「有空時」 | 具體日期，或只寫 P 級，兩者擇一 |
| 模糊範圍：「相關頁面」「部分使用者」「某些情況下」 | 具體路徑、具體條件：「`/checkout` 在 iOS Safari 17.4、購物車超過 20 項時」 |
| 驗收條件寫成形容詞：「功能正常」「效能提升」「體驗更好」 | 指令 ＋ 預期輸出（見下節） |
| 「建議可以考慮⋯⋯」 | 工單是要求，不是建言。直接寫要做什麼 |
| 條列式背景鋪陳半頁 | 只留接手的人不知道的那部分，其餘給連結 |
| 四字格填空：「全面梳理」「深入分析」「持續追蹤」 | 換成一個可執行的動作 |
| 每個範本欄位都填滿散文 | 空白或 N/A 是合法值 |
| 「優先級：高（因為此問題影響較大，若不處理可能導致⋯⋯）」 | 「P1」。理由段落刪掉；真的需要理由就一句話 |

## 五、可測驗收條件的中文寫法（〔骨幹〕＋〔中文推論〕）

規則：**一行指令，一行預期輸出。**用半形程式碼區塊，區塊內不要出現全形標點。

✗ 修好後重新部署佇列功能應正常運作。

✓
```
pytest tests/test_retry.py::test_redeploy_keeps_jobs -q
# 預期：1 passed
redis-cli LLEN jobs:pending
# 預期：worker 重啟後仍為 12（重啟前也是 12）
```

效能類同理：✗「回應時間明顯改善」→ ✓「staging 壓測（`k6 run load/checkout.js`）p95 < 200ms」。

範圍寫法：

```
範圍內：worker/retry.py 的 requeue()、worker/signals.py 的 SIGTERM handler
範圍外：排程器重寫、worker/metrics.py（另開單）
```

## 六、bug 單的重現段（〔骨幹〕）

必要欄位：版本／環境、確切指令或操作、輸入資料、預期、實際（貼原始輸出，不要轉述）、頻率。

範例骨架：

```
版本：api v2.31.0，Postgres 15.4，macOS 14.5
指令：curl -s -X POST localhost:8080/v1/refund -d '{"order_id":"A-119","amount":0}'
預期：400，錯誤碼 INVALID_AMOUNT
實際：500
      {"error":"internal","trace_id":"5f2a…"}
頻率：amount 為 0 時每次都發生；amount > 0 時未發生（試 20 次）
```

重現不出來時，明寫試過什麼：「在 staging 用同一筆 payload 試 30 次都沒重現；prod 日誌顯示 09-02 14:11 起共 4 次，皆來自同一個帳號。」不要用「偶發」帶過。

## 七、寫完後的重讀檢查（逐條打勾）

1. 標題單獨拿出來看，說的是**結果**還是**活動**？
2. 描述有沒有在複述標題？第一句是不是已經提供了標題沒有的資訊？
3. 每條驗收條件都有指令與預期輸出嗎？有沒有「正常」「改善」這種形容詞？
4. 範圍有沒有寫到檔案／函式，並列出明確不做的部分？
5. bug 單的實際輸出是貼上去的，還是被我轉述成中文了？
6. 引用他人結論、依賴、例外授權的句子，有沒有指名到人或團隊？
7. 有沒有把顯而易見的步驟寫進去？刪掉。
8. 全文搜尋：復現、對齊、排查、落地、用戶、數據、優化、界面、字段、缺省、報錯——還有殘留嗎？
9. 全文搜尋「進行」「予以」「做出」「建議可以考慮」——換成動詞或直接的要求。
10. 接手的人讀完，需不需要再問一個問題才能開始？需要的話，缺的就是那一段。
