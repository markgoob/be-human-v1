# 場景包 — 事故檢討報告（postmortem / RCA）

適用：服務中斷檢討、事故報告、RCA 文件、對內或對外的事故說明。

信心標示：〔骨幹〕＝繼承自 sepia 英文場景規則，其原始依據為英文語料（grounded）。〔中文推論〕＝把該規則延伸到中文寫作的判斷，無中文語料量測（inference）。〔推測〕＝未經驗證的建議。凡標〔中文推論〕者，是我們對中文事故文件的判斷，不是量測結果。

---

## 一、結構骨幹（〔骨幹〕，不因語言改變）

1. **絕對時間軸，含時區，且必須包含走錯的路。** 「我們在錯誤假設上花了 38 分鐘」是整份文件資訊量最高的一條；模型系統性地刪掉這種「失敗中的失敗」。
2. **失敗機制寫到程式碼／設定層級**：確切的那句查詢、那個旗標、那個上限值、那段 race window。寫的人不知道，那是要去問團隊的問題，不是可以用文字鋪過去的空格。
3. **影響先給數字，敘述在後**：時間長度、失敗請求數、受影響帳號數、金額（若已知）。
4. **每一條行動項都帶負責人與日期**，否則它不是行動項，是感想。
5. **數字一律來自事故當下的實際資料**，不得為了「看起來完整」而估算。
6. **貢獻因素寫成因果鏈**，每個因素要說明它讓什麼變成可能，不是條列一堆並排的名詞。
7. **反事實誠實交代**：什麼機制本來可以擋下來、為什麼它不存在。不寫「系統行為符合設計」這種保面子的句子。
8. **收在行動項**。沒有「文化」「反思」「共勉」段落。
9. 對人無責，對機制無情。一份沒有承認任何一次判斷錯誤的檢討報告，等於還沒寫。

## 二、責任主體必須詞彙化（本包最重要的規則）

中文允許省略主語，這在一般寫作是正確的、要遵守的。但在**負責任語域**裡，省略主語與英文的 “mistakes were made” 在效果上完全相同：句子讀起來通順，責任沒有落點。〔中文推論〕

**規則 ZH-PM-A：責任主體詞彙化**

- **適用範圍**：時間軸每一條、每一條行動項、狀態回報、對外事故回覆、檢討結論。
- **訊號**：一條時間軸或行動項裡，動詞前找不到可指名的施事者——只有無主句、中文被動句（被／遭／獲），或泛稱。
- **預設動作**：把可指名的主體補回句子最前面。依場合選擇顆粒——系統名（`release-bot`、部署 pipeline、API gateway）、角色名（on-call、DBA、發布負責人）、或人名。
- **保留條件（零主語仍然正確的情況）**：同一段落內、主體已在前句出現且中途沒有換人時，後續連接句照中文習慣省略主語。**每條時間軸、每條行動項至少要有一次**，不是每句都要。
- **重讀檢查**：遮住上下文，單獨讀任何一條時間軸，能不能回答「誰／哪個系統做的」。答不出來就是漏了。

**不算數的主體**（這些詞在中文事故文件裡是霧，不是主體）：相關同仁、相關團隊、相關單位、各方、系統層面、部分成員、有關人員、業務側。

**「我們」的條件**：只有當文件標頭已指名這個「我們」是哪個團隊，而且該動作確實是整個團隊做的，「我們」才算數。用「我們」代替某個具體的人或某個具體系統，不算數。

**反向規則 ZH-PM-B：不得憑空指派主體。** 原始材料沒有指出誰做的，就不要為了句子好看而填一個人或一個團隊進去。做法是：句子維持無主，並在該處掛上 `（執行者待確認）`，同時在行動項裡列出誰去查、什麼時候回填。

**中文被動句的陷阱**：「設定被推上正式環境」「服務被拉起」——中文的無主被動句在事故文件裡與 “the change was deployed” 等價，同樣禁止。有施事者就改成主動句；沒有就掛 `待確認`。

範例（✗／✓）：

- ✗ 設定檔在未經驗證的情況下被推送至正式環境，導致服務異常。
- ✓ 部署 pipeline 在 `config-validate` job 還在排隊時就把 `gateway.yaml` 推上 prod，API gateway 於 14:03 開始回 502。
- ✗ 經排查後，相關同仁已完成修復，目前運作正常。
- ✓ 李維在 14:51 把 `upstream_timeout` 改回 `30s` 並重啟 gateway，錯誤率在 14:53 回到 0.2%（與事故前七日基準相同）。
- ✓（主體不明時）14:20，`worker-3` 被手動重啟（執行者待確認，SRE 週會前由王思婷查 bastion 稽核日誌回填）。

## 四、中文特有的 AI 痕跡（〔中文推論〕）

| 痕跡 | 修法 |
|---|---|
| 開場自我檢討腔：「在本次事件中，我們深刻體認到⋯⋯」 | 刪掉。第一段就是影響數字 |
| 四字格堆疊：「全面梳理、深入排查、持續改善」 | 這是中文版的 generic lessons。換成一條帶負責人與日期的具體改動 |
| 速度自誇副詞：「迅速定位」「第一時間介入」「高度重視」 | 刪掉形容詞，讓時間戳說話：14:03 告警、14:11 有人接手 |
| 輕動詞贅語：「進行修復」「做出調整」「實施重啟」「予以確認」 | 「修好」「調整」「重啟」「確認」。中文的 nominalization padding |
| 「性」「化」後綴堆疊：「可維護性的提升」「流程的標準化建設」 | 「比較好維護」「把 X 步驟寫進 checklist」 |
| 對仗排比：「不僅⋯⋯更⋯⋯」「既要⋯⋯也要⋯⋯」 | 事故文件不需要修辭平衡。拆成兩個獨立事實句 |
| 模糊歸因：「由於多重因素疊加所致」 | 承諾一條你相信的因果鏈；真正不知道的部分明寫「未知」 |
| 無來源的圓整數字：「影響約數千名使用者」 | 用事故資料的實際值。只有估計值時，寫出估計方法與區間 |
| 結尾道德總結：「持續精進，確保服務穩定」 | 收在最後一條行動項 |
| 「後續將持續關注」 | 沒有負責人與日期的句子，不是行動項。補上或刪掉 |
| 範本每一格都填成等長段落 | 「本次做得好的地方」若只有一句誠實的，就只寫一句；沒有就留空或寫 N/A |
| 「該問題已修復完畢，目前運行正常」 | 加上驗證方式與時間點：用什麼指標、在哪個時間看到它回到什麼值 |

## 五、密度與版面（〔中文推論〕）

- **必須維持最高密度（Tier 1）的區塊**：影響數字、時間軸、失敗機制、行動項。這幾段裡每一句都應該帶一個可查證的量或名。
- **允許較低密度的區塊**：一句話的系統背景（給不熟這個服務的讀者）。上限一到兩句。
- **時間軸格式**：`HH:MM (UTC+8)` ＋ 主體 ＋ 動詞 ＋ 具體對象。時間戳、版本號、路徑、指令一律半形，不加全形標點。中文敘述句的句號、逗號、頓號用全形；引述訊息或名稱用「」。
- **走錯的路要留在時間軸裡**，並明講它是錯的方向與花了多久。
- **編輯範圍互動**：`in-place` 範圍下，空洞的整段（例如純套話的「經驗總結」）只能標記回報，不能刪；`bounded` 範圍下，整句刪除要進使用者確認清單；`structural` 才可直接重排。事實不可增刪、責任歸屬不可改寫，這三種範圍都一樣。

## 六、寫完後的重讀檢查（逐條打勾）

1. 遮住上下文讀任一條時間軸，答得出「誰／哪個系統做的」嗎？
2. 每條行動項都有負責人名與日期嗎？有沒有「相關團隊」這種霧？
3. 時間軸裡有沒有至少一次走錯的路，並註明花了多久？
4. 失敗機制是否寫到那個確切的設定值、查詢或旗標？還是停在「設定有誤」？
5. 影響段落的第一句是不是數字？數字是不是來自事故資料而非估算？
6. 有沒有承認任何一次判斷錯誤？完全沒有，就是還沒寫完。
7. 全文搜尋：復盤、根因、對齊、落地、排查、灰度、兜底、宕機、響應、用戶、數據、優化、閉環——還有殘留嗎？
8. 全文搜尋「進行」「予以」「做出」——後面接名詞的都換成動詞。
9. 最後一段是不是行動項？如果是感想或期許，刪掉。
10. 沒有主體的句子，是不是都掛了 `待確認` 並在行動項裡有人負責回填？
